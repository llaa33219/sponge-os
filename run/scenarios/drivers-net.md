# Driver packages, NIC, and the hardware matrix

Breadcrumb: [`run/README.md`](../README.md) → Driver packages, NIC, and the hardware matrix

Driver packages through the stock package flow, framebuffer exclusivity
and the runtime fb switch, NIC smoke tests, the high-phys IO_MEM gate,
and the QEMU hardware matrix. Full catalog entries follow verbatim
(cautions and limitations included); the parent index carries one-line
summaries.

## Scenarios
- `sponge-pkg-driver.run` — **driver packages** (docs/12-package-format.md
  §4.5): installs the `pc_nic` **driver** package through
  `sponge_pkgd`'s ordinary install channel and gates, in order:
  (1) pkgd answered `status="ok"`; (2) `driver_runtime`'s **own**
  sandbox state report lists `pc_nic` as a child — that report is
  generated by `driver_runtime`'s init from its own child table, so the
  name can only be there if the pkgd-generated config was delivered and
  the component was really created; (3) the e1000e driver binds the
  QEMU e1000 (`Intel(R) PRO/1000 Network Driver` — this line only
  exists if the driver attached to the PCI device); (4) `nic_router`
  leases `10.0.2.15` from QEMU's slirp DHCP. The topology is the
  product shape (Tier-0 hardware + a `system` sandbox holding
  `report_rom`, `sponge_pkgd` and TWO sibling nested runtimes,
  `driver_runtime` and `pkg_runtime`) reduced to the components the
  claim needs. base-sel4 only.
  `driver_runtime.inc` (sourced by the desktop-disk product scenarios)
  holds everything shared with them: the driver package list, the HID
  fragments, the quota arithmetic and the staging step. **HID gotcha
  that cost real time:** a `#` comment containing the inline separator
  `|` is NOT a comment — Genode's HID parser splits on `|` first, so
  such a line becomes a node and fails schema validation (or silently
  mis-nests). Keep `|` out of HID comments, and keep a config fragment
  that is substituted into a HID text free of leading indentation on
  its first line, or it lands one level deeper than intended.

- `sponge-pkg-driver.run` also carries two **framebuffer exclusivity
  probes** (docs/12-package-format.md §4.6): extra `driver_probe`
  instances (`fb_lock_probe` / `fb_conflict_probe`) meant to install
  `fb_vesa` and then assert that installing `fb_boot` is refused with
  `exclusive-conflict` naming the incumbent. **They do not prove that
  today:** both probes stop at start on a pre-existing `report_rom`
  policy gap — verbatim `Error: stop because parent denied ROM-session:
  label="result"` (no report_rom policy serves a `result` ROM to either
  probe) — and the scenario's final PASS string is unconditional, so
  **no fb or exclusivity claim is taken from this scenario** (the
  docs/12 §4.6 honest scope note;
  `docs/evidence/phase16-runtime-sweep.md` §8 B3). The exclusivity
  refusal is proven by `run/sponge-pkg-exclusive` (synthetic pair,
  red-first + green, with the byte-identical duplicate-replay receipt).
  The runtime *handover* itself (remove, install, the screen coming
  back) is `run/sponge-desktop-disk.run` with `SPONGE_FB_SWITCH=on`,
  via `test/fb_switch_probe`.

- `sponge-desktop-disk.run` with `SPONGE_FB_SWITCH=on` — the
  **runtime framebuffer-driver switch** proof in the product topology
  (docs/17 §1, docs/15 §8.2). The framebuffer driver is a package, so
  the media's bake manifest seeds one (`fb_vesa` on BIOS, `fb_boot` on
  UEFI) and `sponge_pkgd` starts it inside `driver_runtime`; the arm
  adds `test/fb_switch_probe`, which asserts the seeded driver is a
  `driver_runtime` child, that the composited screen shows a rendered
  desktop, that `remove` + `install` moves the driver to the other fb
  package, and that the screen comes back and SETTLES on a rendered
  desktop. The probe's last line is the gate; it exits 1 with the
  failing phase named if anything inside it fails.

- `sponge-net-probe.run` — Phase 7 todo 12: networking probe on
  base-sel4, proving the stack BEFORE Falkon arrives (todo 16). The
  dde_ipxe e1000 NIC driver (`ipxe_nic`, an Uplink client) is bridged
  to a Nic session by `nic_uplink` (the no-`nic_router` pattern from
  upstream `os/run/nic_uplink.run` — `nic_router` is explicitly out of
  Alpha scope). `fetchurl` (libcurl + libc) loads the `lwip` vfs
  socket plugin at `/socket`, DHCP-configures via lwip, and GETs
  `http://10.0.2.2:8765/net-fixture.txt` from a host-side
  `python3 -m http.server` started by the run script (lifecycle:
  spawned before `build_boot_image`, killed by PID + pkill fallback at
  end-of-run). The fixture's first line is read off the file BEFORE the
  run and the run gates on that exact byte string appearing in the
  boot log (the `misleading_success_output` adversarial class — exit 0
  alone is not enough; the bytes must round-trip). Also starts the
  `system_clock` subsystem (`pc_rtc` + `system_rtc`) so the Rtc
  session TLS will need later is proven to come up on seL4. Bounded
  `run_genode_until` timeouts everywhere (the `hung_or_long_commands`
  class). base-sel4 only (`assert {[have_spec sel4]}`).

- `sponge-high-phys-probe.run` — QEMU-verifiable gate for the
  row-13/14 high-phys IO_MEM machinery (docs/11 §10.6). The probe
  (`repos/sponge/src/test/high_phys_probe`) requests IO_MEM @16 GiB
  (inside the row-13 HIGH device-untyped coverage but outside RAM
  and every e820 region in QEMU — the same class as the 17ZD90N's
  xHCI BAR at 0x601d140000) and expects a mapped dataspace, then
  IO_MEM @2 TiB (beyond the 1 TiB coverage ceiling, inside the
  kernel window) and expects a clean refusal. Gates on
  `high-phys-probe: PASS`. Runs at `-m 4G` because the
  SeaBIOS/default-GRUB chain at RAM > 4 GiB hits a pre-existing
  frame-conversion collision (docs/11 §10.6) unrelated to this
  machinery. base-sel4 only.

- `sponge-pc-nic.run` — **Phase 12 — Phase-12 criterion 2 expanded
  driver set (pc_nic/e1000 + nic_router DHCP)**. Additive
  Linux-backed NIC driver smoke on q35+Skylake-Client: the in-tree
  `pc_nic` server (`genode/repos/pc/src/driver/nic/pc/`) is built from
  the Phase-12-managed `pc` repository (added to `REPOSITORIES` in
  W1, idempotent), QEMU exposes `-device e1000`, and the upstream
  `nic_router` policy `label_prefix: pc_nic | domain: uplink` is
  copied verbatim. `pc_nic` is sized `caps: 1000 | ram: 32M` (the
  Phase-12 small-box; the upstream default of ~140 caps / 16 MiB
  silently hangs on seL4). QEMU's user-mode slirp backend is preserved
  (no tap/bridge). Gates in order: `pc_nic: bound device` then
  `nic_router: uplink DHCP acquired` (300 s cold DDE-Linux gate;
  the bounded timeout is a loud failure, not a silent hang). The
  existing `run/sponge-net-probe.run` (iPXE/fetchurl round-trip) is
  unchanged. Evidence `docs/evidence/phase12-pc-nic.log`. **Honest
  claim text** (per docs/15 row):
  "pc_nic = Linux-NIC-driver stack (e1000e/rtl8169/ath9k/iwlwifi/rtlwifi/USB-Ethernet). QEMU-verified on `-device e1000` only; rtl8169/Wi-Fi/-USB-Ethernet documented but NOT QEMU-tested."

- `sponge-hw-matrix.run` — Phase 16 pre-real-hardware gate: the
  proven interactive driver stack with ONE QEMU emulated-hardware
  axis varied per run via env knobs (`SPONGE_HW_VARIANT/CPU/SMP/
  MEM/MACHINE/VGA/USB/INPUT/IOMMU`, plus the raw `SPONGE_HW_EXTRA`
  and `SPONGE_HW_TSCALE` escape hatches), QMP-driven input
  interaction per mode (tablet/mouse/kbd/ps2/multi — hotplug audit
  chains, PS/2 stability window), and a fail-loud
  `sponge-hw-matrix: PASS (variant=...)` marker. Driven by
  `./tool/hwtest` (20-variant default matrix, PASS/FAIL table);
  manual escape hatch documented in `docs/08-development.md` §16.
  Known boundaries: XSAVE-less CPUs, `-vga cirrus`, the TCG boot
  race, `-no-hpet`. base-sel4 only.
